📊 Data Inputs

🛰️ Satellite Himawari-8/9 L1b — B08, B11, B13 bands
📡 Sensor Temperature, humidity, rainfall, PM2.5, wind (speed + direction)
📍 Location GPS coordinate embedding + hour/month cycle

Core idea: Combine satellite imagery (cloud patterns) with ground sensor readings (temperature, humidity, wind) to predict rainfall at any GPS coordinate in Singapore, 10 minutes ahead.

The system evolved from a single-channel IR satellite model to a 3-channel multi-sensor fusion architecture over 11 versions in 25 days.

Key innovation: Local Patch + Coordinate Embedding — instead of looking at the entire satellite image, the model crops a 32×32 pixel patch directly above each station, learning "will the cloud overhead produce rain here?"

Built with React + FastAPI + PyTorch on AWS (EC2 + S3)

Key decisions:

  • v1 → v2: JAXA FTP was slow and unreliable across the ocean. Migrated to AWS same-region for speed.
  • v2 → v3: 10.1TB of raw NetCDF accumulated on S3 ($53/mo). Switched to L1b HSD — 23,000× smaller per file, 3 channels instead of 1.

3-channel advantage:

  • B08 (6.2μm) — Water vapor / moisture
  • B11 (8.6μm) — Cloud phase (ice vs liquid)
  • B13 (10.4μm) — Cloud top height

Together, these let the model distinguish rain-producing cumulonimbus from harmless cirrus clouds.

Impact: +15-25% expected precision improvement

  • Regional (PM2.5) — region-level, mapped to nearest station

Key lesson: When downloading 6 years of historical data across a satellite transition boundary, file naming conventions and bucket locations are not uniform.

These issues were discovered progressively during the download — none are documented in the AWS Open Data catalog.

The pipeline must be resilient to:

  • ~2-5% of timestamps missing per day (satellite outage/maintenance)
  • Bucket name changes mid-dataset
  • Filename prefix changes
  • Network throttling during burst downloads

Why per-station training?

Singapore is small (~50km) but microclimates differ significantly. A single model trained on all stations averages out local patterns.

Each station's training data pairs its sensor readings with a 32×32 satellite patch directly overhead. The model learns "will it rain at this location" rather than "will it rain somewhere in Singapore."

Selection criteria:

  • High data completeness
  • Geographic spread across NEA regions
  • Pedestrian relevance
  • Microclimate diversity (coastal, urban, open)

🎯 Rain Threshold Evolution

Threshold Rain % F1 Problem
0.1mm 30.3% 46.6% Too sensitive — drizzle triggers
5.0mm 2.0% 35.7% Too strict — can't learn
1.0mm ✅ 13.0% 61.5% "Need an umbrella" rain

Key insight — R4 breakthrough:

Instead of feeding the entire 128×128 satellite image, R4 crops a 32×32 patch centered on the target station. This forces the model to focus on the cloud directly overhead.

Combined with coordinate embedding (station lat/lon + hour/month cycle encoding), the model can distinguish afternoon convective rain (2-6 PM) from morning false signals.

Rain threshold: 0.1mm captured insignificant moisture. 5.0mm was too rare (<2%). 1.0mm = the rain intensity a pedestrian would notice and want to avoid.

Training: 80s/epoch on g4dn.xlarge GPU (NVIDIA T4)

Why not Databricks / Snowflake?

  • Our data volume (~6GB processed) is too small to justify cluster overhead
  • Custom binary format (.npy tensors) doesn't fit SQL/tabular paradigm
  • Need direct GPU access for custom CNN+LSTM fusion model
  • Managed platforms add $100-200/mo without benefit

Key decisions:

  • 3-server split: decouple data-intensive from latency-sensitive
  • S3 as data lake: "Just-in-Time" processing (150GB raw → 5MB patches → purge)
  • Spot Instance for training: 70% cost saving, acceptable for batch ML

Reconsider managed platforms at >100GB or team size >3
