# Architecture Decision Record (ADR)

本文档记录 Weather AI 项目中的关键技术决策，方便团队回溯设计意图。

---

## ADR-001: 多通道卫星波段选择

**日期**: 2025-02-17
**状态**: 已采纳

### 决策
使用 **B08 + B11 + B13** 三个 AHI 波段作为模型输入。

### 背景
Himawari-8/9 AHI 传感器有 16 个波段，需要选择与降雨预测最相关的 3 个。

### 考虑的方案

| 波段 | 波长 | 信息 | 选中 |
|------|------|------|------|
| B08 | 6.2μm | 高层水汽 → 大气湿度 | ✅ |
| B11 | 8.6μm | 云相态（冰晶 vs 水滴）→ 区分积雨云和卷云 | ✅ |
| B13 | 10.4μm | Clean IR Window → 云顶高度/对流强度 | ✅ |
| B14 | 11.2μm | IR Longwave → 与 B13 高度相关，信息冗余 | ❌ |

### 理由
- B14 与 B13 相关性极高，替换为 B11 可获得独立信息维度
- B11 对冰/水相态敏感，可区分积雨云（降雨）和卷云（不降雨）
- 3 通道组合覆盖：湿度 + 云类型 + 云高度

## ADR-002: 保留原始分辨率，不 Resize

**日期**: 2025-02-17
**状态**: 已采纳

### 决策
裁剪后的卫星图保持原始分辨率 **(41×37)**，不 resize 到 128×128。

### 理由
- 避免 bilinear 插值引入伪影
- 模型 `AdaptiveAvgPool2d` 已支持任意输入尺寸
- 41×37 ≈ 1,500 像素 vs 128×128 = 16,384 像素，计算量降低 ~10 倍

## ADR-003: 全图入模型，不 Crop Patch

**日期**: 2025-02-17
**状态**: 已采纳

### 决策
所有气象站共享同一张 41×37 全图（覆盖新加坡+柔佛新山），通过 `coord` 输入传递站点位置。

### 旧方案
每个站从 128×128 图裁 32×32 patch（仅看头顶 ~10km）。

### 新方案优势
- CNN 能看到 ~70km 范围内正在逼近的云团
- 热带对流降雨的云团经常从周边移过来，只看头顶会错过
- `coord` 让模型自学空间关系，比硬裁剪更灵活

## ADR-004: 数据源选择 AWS Open Data

**日期**: 2025-02-17
**状态**: 已采纳

### 决策
使用 AWS Open Data S3 (`noaa-himawari8/9`) 下载 L1b HSD 文件，而非 JAXA FTP。

### 理由
- Download server 在 AWS 同区域，S3 传输速度远快于跨洋 FTP
- S3 支持并行下载，无连接数限制
- 免费无需认证（`UNSIGNED` config）

## ADR-005: 处理后上传 S3 并删本地

**日期**: 2025-02-17
**状态**: 已采纳

### 决策
卫星数据 `保存本地 → 上传 S3 → 删除本地文件`，skip 判断通过 `head_object` 检查 S3。

### 理由
- Download server 磁盘空间有限（~8GB 可用）
- 全量 ~97 万文件约 6GB，会耗尽磁盘
- S3 存储便宜且持久

### 存储路径
```
s3://weather-ai-models-de08370c/processed/satellite-3ch/
  SAT_B08_YYYYMMDD_HHMM.npy
  SAT_B11_YYYYMMDD_HHMM.npy
  SAT_B13_YYYYMMDD_HHMM.npy
```

**日期**: 2025-02-17
**状态**: 已采纳

### 决策
卫星裁剪区域从仅新加坡扩展到 **新加坡 + 柔佛新山**。

### 坐标
```
SG_LON_MIN = 103.5   SG_LON_MAX = 104.2

```

### 理由
- 柔佛方向的云团是新加坡北部降雨的主要来源之一
- 扩大视野有助于模型学习云团移动趋势

**日期**: 2025-02-17
**状态**: 已采纳

### 决策
Himawari 全盘有 10 个 segment，只下载 **S0510**（12°N ~ 0°N）。

### 理由

## ADR-009: 下载服务器升级 t3.large → t3.xlarge

**日期**: 2026-02-17
**状态**: 已采纳

### 背景
8 workers 在 t3.large (8GB) 上运行时触发 OOM Kill（python3 占 7.3GB），进程被系统杀死。Watchdog 自动重启后降为 4 workers 继续运行，但速度减半。

### 决策
升级到 **t3.xlarge** (4 vCPU / 16GB)，最终使用 12 workers。

### 性能矩阵

| Workers | 实例 | 内存占用 | 速度 (文件/分) | 预计总时间 | 预计总费用 | 状态 |
|---------|------|---------|---------------|-----------|-----------|------|
| 4 | t3.large (8GB) | 1.5GB | ~53 | ~13 天 | ~$32 | OOM 后降级 |
| 8 | t3.xlarge (16GB) | 2.4GB | ~69 | ~9-10 天 | ~$45 | 升级后初始 |
| **12** | t3.xlarge (16GB) | **2.5GB** | **~107** | **~6 天** | **~$30** | ✅ **当前** |

> 12 workers 较 4 workers 提速 **2×**，较 8 workers 提速 **55%**，内存仅增 0.1GB，总费用最低。

### 后续
下载完成后应降回 t3.large 或停止实例以节省费用。

## ADR-010: 下载脚本三项性能优化

**日期**: 2026-02-17
**状态**: 已采纳

### 背景
12 workers 在 t3.xlarge 上 CPU 占 88%（load average 6.41 > 4 核），接近饱和。

#### 瓶颈排查

| 可能瓶颈 | 实测 | 结论 |
|---------|------|------|
| S3 API 限流 | ~1.8 req/s（限制 5,500/s） | ❌ 余量 3000× |
| AWS Open Data 限流 | ~54KB/s, 无显式配额 | ❌ 远低于阈值 |
| 网络带宽 | t3.xlarge baseline ~1.25Gbps | ❌ 文件仅 30KB |
| **CPU (satpy + GIL)** | **88% us+sy, idle 10.7%** | ✅ **主要瓶颈** |
| 内存 | 2.5GB / 16GB | ❌ 余量充足 |

#### 备选方案（未采纳）

| 方案 | 原因 |
|------|------|
| 换 c6i.xlarge | 单核性能 +30%，但软件优化已足够 |
| 升级 t3.2xlarge (8 vCPU) | 多花 ~$10 只快 2 天，性价比低 |

### 决策

#### 1. HSD 直接解析替代 satpy
新增 `hsd_parser.py`，直接用 `bz2.decompress` + `struct.unpack` + `np.frombuffer` 解析 HSD 二进制文件，跳过 satpy 的 Scene/reader/dask/xarray 链。

- 回归验证: 3 波段 max diff < 0.0001K（与 satpy 对比）
- 本地实测: **1.8× 加速**
- crop bounds `(455, 496, 891, 928)` 为 satpy 验证过的固定常量

#### 2. completed_days 本地缓存
新增 `.completed_days` 文件记录已处理日期。重启时跳过已完成天，**零 S3 HEAD 请求**。

原问题: 每个 slot 需 3× S3 HEAD 检查，已完成 100 天 = 43,200 次无用请求 (~40s 延迟)。

#### 3. Thread → Process
`ThreadPoolExecutor` → `ProcessPoolExecutor`，绕过 Python GIL，真正并行利用 4 核 CPU。

每个子进程通过全局变量缓存 S3 client（创建一次，后续复用），额外内存 ~240MB（16GB 中可忽略）。

### 部署结果 (02-17 21:08 实测)

| 指标 | 优化前 (satpy+threads) | 优化后 (hsd+process) | 变化 |
|------|----------------------|---------------------|------|
| CPU | 88% us, 7% sy | 96.5% us, 3% sy | 真并行利用更充分 |
| Load Average | 6.41 (4核) | 9.04 | 12 进程真并行 |
| 内存 | 2.5 GB | 2.0 GB | -20% |
| 网络下载 | — | 9,108 KB/s (~9MB/s) | 带宽利用更高 |
| 处理速度 | ~107 文件/分 | **~237 文件/分** | **+120%** |
| 预计总时间 | ~6 天 | **~3 天** | -50% |
| 预计总费用 | ~$30 | **~$15** | -50% |

### 预期收益

| 优化 | 收益 | 风险 |
|------|------|------|
| HSD 解析 | CPU 减少 ~45% | 已验证, shape/值完全匹配 |
| completed_days | 重启追赶时间 → 0 | 无（纯追加文件） |
| Thread → Process | 多核真并行 | 内存 +240MB，可忽略 |
